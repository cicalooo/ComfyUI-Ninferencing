# NInfer on RTX 6000 Blackwell (Windows and Linux)

Setup for the NInfer application on the RTX 6000 Blackwell family, plus how to pull a normal and an uncensored model from Hugging Face.

This family is the workstation and server cards, not GeForce:

| Card | Compute capability | Memory |
|---|---|---|
| RTX PRO 6000 Blackwell Workstation | 12.0 (`sm_120`) | 96 GB GDDR7 |
| RTX PRO 6000 Blackwell Server | 12.0 (`sm_120`) | 96 GB GDDR7 |
| RTX PRO 6000 Blackwell Max-Q | 12.0 (`sm_120`) | 96 GB GDDR7 |

Confirm before installing:

```bash
nvidia-smi --query-gpu=name,compute_cap,memory.total,driver_version --format=csv
```

`compute_cap` must be `12.0` and the name must be an RTX PRO 6000 Blackwell. GeForce RTX 5090 binaries are a different target (`sm_120a`). Cubins built only for `120a` do not run on this family. RTX 6000 Ada is a different card (`sm_89`) and is not covered here.

Published NInfer builds and tok/s numbers are for a 32 GB RTX 5090. They are not measurements for this GPU. There is no packaged NInfer zip qualified for `sm_120`.

## What you are installing

NInfer is a single-GPU C++/CUDA engine. It does not open Safetensors, GGUF, or a Transformers folder. It loads one `.ninfer` file: quantized weights, tokenizer, chat template, and the vision tower.

| Binary | Role |
|---|---|
| `ninfer` | One prompt. Answer on stdout, diagnostics on stderr. |
| `ninfer-serve` | OpenAI `/v1/chat/completions` and `/v1/responses`, Anthropic `/v1/messages`, default `127.0.0.1:8080`. |

Current trees want container **v3** artifacts, an NVIDIA driver that supports CUDA **13.1**, and one resident model per process. `--vision` and `--spec` are fixed at process start. A later HTTP request cannot enable them.

Flags that matter on 96 GB:

- `--kv-dtype int8` — large-context default. BF16 KV is much larger and is not the 96 GB default.
- `--kv-capacity auto` — sizes the KV pool from memory left after weights, leaving about 1 GiB. Use this instead of a 5090 context cap.
- `--max-context` — per-sequence ceiling, up to 262,144. It does not by itself allocate that much KV.
- `--spec mtp --draft-tokens 3 --lm-head-draft` — speculative decode. The artifact must contain the MTP head.
- `--vision` — required before any image or video request.
- `--no-thinking` — skip reasoning traces when you want a short answer.

Start at `--max-context 32768`. Raise it after a clean startup with the desktop (Windows) or other GPU work still resident. 96 GB is enough for the 27B artifact, vision, MTP, and a long INT8 KV pool; it is not a reason to copy a 150k launcher written for 32 GB.

## Application: Windows 11

Native executable. WSL2 is not required.

1. Install a current NVIDIA driver whose `nvidia-smi` header reports CUDA **13.1 or newer**.
2. Get a binary that contains `sm_120` cubins, not only `sm_120a`.

The portable zip on [natpate/ninfer-windows](https://github.com/natpate/ninfer-windows/releases) (`ninfer-windows-<version>-win64-cuda131.zip`) is the Windows application: `ninfer.exe`, `ninfer-serve.exe`, FFmpeg, libcurl, zlib, the VC++ runtime, and launchers. Verify `SHA256SUMS` with `Get-FileHash`. Extract anywhere; launchers use relative paths. Models are not in the zip.

That zip tracks upstream, which compiles `120a` and rejects other architectures. `--help` can succeed and the first model load can still die with an invalid device function or no kernel image. That is the 5090 cubin on an RTX 6000 Blackwell, not a bad download. Do not keep retrying it.

Source build when the zip does not match the card. Requirements: Visual Studio 2022, CMake 3.28+, CUDA Toolkit 13.1+, [vcpkg](https://github.com/microsoft/vcpkg).

```powershell
git clone https://github.com/natpate/ninfer-windows.git
cd ninfer-windows

cmake -S . -B build-windows -G "Visual Studio 17 2022" -A x64 `
  -DCMAKE_TOOLCHAIN_FILE=C:/path/to/vcpkg/scripts/buildsystems/vcpkg.cmake `
  -DVCPKG_TARGET_TRIPLET=x64-windows `
  -DCMAKE_CUDA_ARCHITECTURES=120
cmake --build build-windows --config Release --parallel
```

If configure refuses every architecture except `120a`, that tree is not an RTX 6000 Blackwell port. Changing the allowlist without a kernel schedule that runs on `sm_120` is not a finished build. Use a tree that already accepts `120`.

Outputs:

```text
build-windows\apps\Release\ninfer.exe
build-windows\apps\Release\ninfer-serve.exe
```

Keep the `.ninfer` file on local NTFS, next to the exe or under a `models` folder. Do not memory-map a 17–22 GiB artifact from a network share.

First server start, after section "Models":

```powershell
.\ninfer-serve.exe .\models\qwen3_8_27b.ninfer `
  --host 127.0.0.1 --port 8080 `
  --max-context 32768 `
  --kv-capacity auto `
  --kv-dtype int8 `
  --max-concurrency 2 `
  --spec mtp --draft-tokens 3 --lm-head-draft
```

`--webui` on this port downloads the llama.cpp WebUI once, then reuses the local copy.

```powershell
curl http://127.0.0.1:8080/v1/chat/completions `
  -H "Content-Type: application/json" `
  -d "{\"model\":\"qwen3.8-27b\",\"messages\":[{\"role\":\"user\",\"content\":\"Reply with one short sentence.\"}],\"max_tokens\":64}"
```

The `model` field is the artifact `identity.model_id` printed at startup, not the filename.

## Application: Linux

Same driver rule: CUDA 13.1 or newer in `nvidia-smi`. Compiling also needs the CUDA 13.1 toolkit.

Packages (Debian/Ubuntu names; Arch equivalents are fine): GCC 13, CMake 3.28+, Ninja, `pkg-config`, FFmpeg dev (`libavformat` ≥ 60, `libavcodec` ≥ 60, `libavutil` ≥ 58, `libswscale` ≥ 7), `libcurl` ≥ 7.85.

```bash
git clone https://github.com/natpate/ninfer-windows.git
cd ninfer-windows

cmake -S . -B build -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CUDA_ARCHITECTURES=120
cmake --build build --parallel
```

[Neroued/ninfer](https://github.com/Neroued/ninfer) is the same engine without the Windows port. It has the same `120a` lock. Prefer one tree for both operating systems, and the same `sm_120` configure check as Windows.

```text
build/apps/ninfer
build/apps/ninfer-serve
```

Install layout:

```text
/opt/ninfer/releases/<version>/
/opt/ninfer/current -> releases/<version>
```

Store weights on a Linux filesystem (`$HOME/models/ninfer`). Do not put the artifact on NTFS.

Docker only if you build the image on this GPU, so the cubins are `sm_120`, and the NVIDIA Container Toolkit is installed:

```bash
docker build --tag ninfer:local .
docker run --rm \
  --gpus '"device=0"' \
  --publish 8080:8080 \
  --volume "$PWD/models:/models:ro" \
  ninfer:local \
  ninfer-serve /models/qwen3_8_27b.ninfer \
  --host 0.0.0.0 \
  --max-context 32768 \
  --kv-capacity auto \
  --kv-dtype int8 \
  --spec mtp --draft-tokens 3 --lm-head-draft
```

`--host 0.0.0.0` is for inside the container. On the host, bind `127.0.0.1` unless the API is meant to be reachable from other machines.

## Models from Hugging Face

Install the client once:

```bash
pip install -U huggingface_hub
```

`hf download` is resumable. A token is optional on these public repos. Download the `.ninfer` file only. The BF16 Qwen tree is about 55 GB and NInfer cannot open it.

Current Blackwell engines want container **v3**. If the server reports a bad artifact magic or container version, the file is an older conversion, not a GPU fault. A v2 file can be upgraded in place with `tools/upgrade_ninfer_v2_to_v3.py` from the Windows-port tree. A v1 file cannot.

### Normal

Official quantized conversions of the aligned Qwen checkpoints. Apache-2.0. This is the default on an RTX 6000 Blackwell.

| Model | Repo | File |
|---|---|---|
| Qwen3.8-27B groupwise-int | [neroued/Qwen3.8-27B-NInfer](https://huggingface.co/neroued/Qwen3.8-27B-NInfer) | `qwen3_8_27b.ninfer` |
| Qwen3.8-27B NVFP4 | [neroued/Qwen3.8-27B-nvfp4-NInfer](https://huggingface.co/neroued/Qwen3.8-27B-nvfp4-NInfer) | `qwen3_8_27b_nvfp4.ninfer` |
| Qwen3.6-27B groupwise-int | [neroued/Qwen3.6-27B-NInfer](https://huggingface.co/neroued/Qwen3.6-27B-NInfer) | `qwen3_6_27b.ninfer` |
| Qwen3.6-27B NVFP4 | [neroued/Qwen3.6-27B-nvfp4-NInfer](https://huggingface.co/neroued/Qwen3.6-27B-nvfp4-NInfer) | `qwen3_6_27b_nvfp4.ninfer` |
| Qwen3.6-35B-A3B | [neroued/Qwen3.6-35B-A3B-NInfer](https://huggingface.co/neroued/Qwen3.6-35B-A3B-NInfer) | `qwen3_6_35b_a3b.ninfer` |

Use groupwise-int Qwen3.8-27B unless you specifically want the NVFP4 speed profile or the 35B MoE. On 96 GB, NVFP4 is optional. DFlash on the 35B artifact is text-only.

Linux:

```bash
mkdir -p "$HOME/models/ninfer"
hf download neroued/Qwen3.8-27B-NInfer \
  qwen3_8_27b.ninfer SHA256SUMS \
  --local-dir "$HOME/models/ninfer/Qwen3.8-27B-NInfer"
cd "$HOME/models/ninfer/Qwen3.8-27B-NInfer"
sha256sum -c SHA256SUMS
```

Windows:

```powershell
mkdir models -Force
hf download neroued/Qwen3.8-27B-NInfer `
  qwen3_8_27b.ninfer SHA256SUMS `
  --local-dir .\models\Qwen3.8-27B-NInfer
Get-FileHash .\models\Qwen3.8-27B-NInfer\qwen3_8_27b.ninfer -Algorithm SHA256
```

Check the hash against `SHA256SUMS` in that repo. Do not use a hash copied from an old README. The Qwen3.8 groupwise file has already moved (v2 was 16.96 GiB; later v3 builds are larger, about 19 GiB). A mismatch is a partial download or a different revision.

Point the server at that path:

```text
ninfer-serve /path/to/qwen3_8_27b.ninfer --host 127.0.0.1 --port 8080 ...
```

### Uncensored

An uncensored Qwen3.8-27B `.ninfer` file is the same engine format with refusal-removed weights. It is not a different runtime. Public BF16 sources are [orcarouter/Qwen3.8-27B-Uncensored](https://huggingface.co/orcarouter/Qwen3.8-27B-Uncensored) and [JonathanColetti/Qwen3.8-27B-Uncensored](https://huggingface.co/JonathanColetti/Qwen3.8-27B-Uncensored). NInfer cannot serve those folders. They have to be converted by NInfer's converter (`tools.convert` in the engine tree), which also grafts the official Qwen tokenizer and chat template.

Preconverted community files are not the neroued artifact and are often the wrong container version for a current Blackwell binary.

The widely mirrored file is a **v1** conversion built for Ada/3090 forks, not for this GPU:

| | |
|---|---|
| Repo | [pyros-vault/Qwen3.8-27B-Uncensored-NInfer](https://huggingface.co/pyros-vault/Qwen3.8-27B-Uncensored-NInfer) |
| File | `Qwen3.8-27B-Uncensored.ninfer` |
| Size | 18,210,531,328 bytes (16.96 GiB) |
| SHA-256 | `314e2812942b2b078f341530f6f5f5e46d79b08d668b77ed4d8f58e12fda41f4` |
| Recipe | `qwen3_8_27b-v1` |

Do not drop that file on the RTX 6000 Blackwell engine. A v3 server will reject the container. Other uploads (DogOnKeyboard, fullmetaljackass, DreamFast, and similar) are usable only when their conversion report says container v3, identity `qwen3.8-27b`, and the SHA-256 you compute matches the repo.

To get an uncensored artifact this binary will load, convert the BF16 checkpoint with the **same** NInfer revision you serve:

```bash
# from the NInfer source tree, after the official frontend files are staged
python3 -m tools.convert.qwen3_8_27b.convert \
  --model /path/to/Qwen3.8-27B-Uncensored \
  --out "$HOME/models/ninfer/Qwen3.8-27B-Uncensored.ninfer" \
  --device cuda
```

Keep the Uncensored filename. Do not rename it to `qwen3_8_27b.ninfer`. Both files can advertise `model_id` `qwen3.8-27b`; the server uses the path you pass, and a client should be pointed at the process you started, not at a shared name.

[j842/ninfer-qwen-uncensored](https://github.com/j842/ninfer-qwen-uncensored) is a pinned convert of `JonathanColetti/Qwen3.8-27B-Uncensored`. That repo does not publish the `.ninfer` file. Use it when you want a known converter commit rather than an anonymous upload. Disk for a from-scratch convert is on the order of 90 GB (BF16 shards plus the artifact).

Serve it with the same flags as the normal artifact. Bind `127.0.0.1`. Do not leave an uncensored server on a shared address. Use the neroued file when you want the aligned Qwen weights.

| Goal on this GPU | File |
|---|---|
| Aligned Qwen3.8 | `qwen3_8_27b.ninfer` from `neroued/Qwen3.8-27B-NInfer`, hash checked against that repo's `SHA256SUMS` |
| Refusal-removed Qwen3.8 | A v3 `.ninfer` converted by the same engine revision. Not the v1 file SHA `314e2812…`. |

## ComfyUI

The **Ninferencing** node does not embed the engine. It runs whatever `ninfer` it finds: `NINFER_EXECUTABLE`, then `NINFER_HOME`, then `/opt/ninfer`, `/opt/ninfer/current`, an older `/opt/ninfer-3090/current` layout, `~/.local/ninfer`, `PATH`, then `C:\ninfer\ninfer.exe`.

Point it at the Blackwell binary so it does not pick up another install:

```bash
export NINFER_EXECUTABLE=/opt/ninfer/current/ninfer
export NINFER_MODELS_DIR="$HOME/models/ninfer"
```

On Windows, set `NINFER_EXECUTABLE` to the full path of `ninfer.exe` and `NINFER_MODELS_DIR` to the folder that holds the `.ninfer` files. Restart ComfyUI and refresh node definitions after adding a file.

96 GB removes the 24 GB KV limits. Raise the node `context_length` and leave Settings `kv_capacity` on `auto` or `match_context`. Pass vision only on nodes that send images or video. One NInfer process at a time. The node can unload Comfy-owned models; it cannot free VRAM held by another application.

## Failures

| Symptom | Cause |
|---|---|
| Invalid device function, no kernel image, CUDA launch failure | Binary is `sm_120a` (5090 zip or an unpatched upstream build). Rebuild with `CMAKE_CUDA_ARCHITECTURES=120`. |
| Artifact magic / container version error | v1 or v2 file on a v3 engine. The uncensored SHA `314e2812…` is v1. Use the official v3 download, or convert again with this engine. |
| HTTP 404 on the model name | Request `model` does not match the startup `model_id`. |
| ComfyUI still launches a 30/40 `ninfer` | `NINFER_EXECUTABLE` is unset and `/opt/ninfer` exists. Set the variable to the Blackwell binary. |
